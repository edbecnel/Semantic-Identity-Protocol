1

Overview

This mockup demonstrates SIP Semantic IntelliSense — an interactive resolver for Semantic Identity Paths (SIPs). A SIP is a dot-separated string that encodes human-readable meaning rather than a file path or URL. For example, @games.strategy.abstract.capture.leaping.columns.lasca uniquely identifies the Lasca board game concept through a chain of semantic categories.

The mockup is entirely self-contained. It uses no external libraries, makes no network requests, and requires no build step. Everything you interact with — paths, owners, shortcuts, synonyms — is hard-coded mock data that illustrates how a real resolver would behave.

The central distinction: Typing categories explores meaning. Choosing an owner-bound result commits identity. Discovery paths return ranked candidates; owner-bound paths can resolve deterministically to a single destination.
2

The SIP input

The main text field in the Active SIP input card is where you type or paste a SIP string. The @ prefix is displayed as a fixed prompt mark to the left; you do not need to type it.

Triggering suggestions

Type a trailing dot after any segment to request the next level of semantic suggestions. For example, typing games. shows all child segments of the games category. You can also click the Add trailing dot button.

If the current path has a registered semantic (shortcuts, synonyms, owner candidates, or broad facets), suggestions appear even without a trailing dot once you have two or more segments.

Mode indicator

The pill in the top-right corner of the card shows the current mode:

  • Discovery path — Unbound semantic exploration. The path has meaning but no committed owner.
  • Owner-bound identity — The first segment is an owner namespace (e.g. @stackworks.…). The resolver can deterministically route to a destination.
  • Shortcut discovery path — A compact alias such as @games.lasca that expands to a longer discovery path.
  • Broad semantic facet — A cross-cutting mechanic (e.g. stacking) that matches several narrower branches rather than a single canonical path.
  • Personal shortcut binding — A user-saved shortcut that resolves within this session to a specific owner-bound SIP.
3

Suggestion types

The IntelliSense panel shows up to six distinct groups, each marked with a coloured badge. Groups appear only when relevant data exists for the current path.

saved shortcut Saved personal shortcut binding. Shown when the current input exactly matches a shortcut you have saved this session. Offers to expand the shortcut to its full canonical SIP, or clear it.
shortcut alias Shortcut SIP expansion. A predefined compact alias that expands to a longer discovery or owner-bound path. Clicking the row replaces the input with the expanded form.
synonym Semantic synonym / equivalent path. A path segment that carries the same meaning in this context (e.g. columns ⇄ stacking). Clicking rewrites the entire string using the alternative wording.
narrower path Broad semantic facet narrowing. When the current path is a wide-meaning concept, the resolver suggests more precise sub-branches. Clicking replaces the input with the narrower path.
continue path Semantic discovery continuation. Available when you type a trailing dot. Shows valid next-level segments. Clicking appends that single segment to the current string.
bind owner / candidate Owner-bound identities. Registered owners whose SIP overlaps with the current discovery path. In shortcut-binding context, you can open once or save as your shortcut. Outside that context, clicking rewrites the string to the canonical owner-qualified identity.
non-canonical prefix Dead-end warning. Shown when the current owner-bound path prefix has no tree entries but matches a known shortcut alias key. The panel offers a ↩ Jump to canonical prefix button that rewrites the input to the resolvable canonical form.

Toggle metadata

Click the Toggle metadata button to expand or collapse extra detail beneath each suggestion — verified owner, destination URL, trust level, and explanatory notes.

Create freeform shortcut

When the current path has at least two segments and a registered semantic, a Create freeform shortcut row appears at the bottom of the panel. Type any alias (e.g. my.lasca) and click Save shortcut to bind it to the current SIP for this session.

4

Resource-type binding

An owner-bound SIP identifies who holds an identity, but it does not inherently tell you what kind of resource the destination offers — is it a place to play, an article to read, a store page to purchase from? SIP supports three coexisting approaches to expressing resource-type intent.

Options A, B, and C demonstrate three different ways a SIP can express what kind of resource a destination offers without changing the underlying concept identity. All three can resolve to the same underlying destination — SIP does not mandate one form. Owners can register any or all of them simultaneously, and the resolver surfaces all registered bindings so the user picks their preferred level of specificity:

  • Option A (terminal qualifier) — Best for discovery across multiple owners. The resource type is named explicitly as the final path segment, so you can browse all owners offering a specific resource type without pre-selecting one.
  • Option B (owner-implicit) — Most concise form. The path stops at the concept level and the resolver infers the resource type from the owner's well-known profile. Works well when the owner is unambiguous and widely known.
  • Option C (namespace intent) — Fully self-describing. An intent segment is inserted between the owner and the discovery path, making the resource type explicit even to someone unfamiliar with the owner.

Option A — Terminal qualifiers

Resource type is expressed as a terminal path segment appended to the concept identity:

@ogs.games.strategy.abstract.territory.enclosure.go.online
Play destination — the online segment disambiguates this binding from a rules or history resource.
@wikipedia.games.strategy.abstract.territory.enclosure.go.rules
Informational destination — Wikipedia article specifically for the rules of Go.

These terminal segments are ordinary semantic children of the concept node. The mockup tree carries them as valid IntelliSense continuations — type @games.strategy.abstract.territory.enclosure.go. and the panel will offer online, rules, strategy, history, and others. (Note: go here is the name of the ancient board game Go, not the verb “to go to” — the segment …enclosure.go is the concept node for that game.)

Option B — Owner-implicit binding

Resource type is inferred from the owner's well-known profile rather than stated in the path:

@ogs.games.strategy.abstract.territory.enclosure.go
OGS is an online Go server, so the destination is implicitly playable. No extra segment is needed.

This approach produces shorter SIP strings and is the default form already in use throughout the mockup. It works best when the owner is unambiguous and widely known.

Option C — Namespace intent

Resource type is inserted as an intent segment directly after the owner namespace, before the discovery path:

@ogs.play.games.strategy.abstract.territory.enclosure.go
Fully self-describing: owner is OGS, intent is play, concept is Go.
@wikipedia.ref.games.strategy.abstract.territory.enclosure.go
Owner is Wikipedia, intent is reference, concept is Go.

The discovery portion of the path remains structurally intact. A resolver or AI assistant can infer intent from the inserted segment without out-of-band knowledge of the owner.

All three coexist

A single owner may register multiple bindings at different levels simultaneously. The resolver presents all registered bindings and lets the user choose the level of specificity they prefer. Which form predominates in practice will emerge from adoption rather than mandate.

bind owner Option B — game-level binding: @ogs.games.…go
bind owner Option A — terminal-qualifier binding: @ogs.games.…go.online
bind owner Option C — namespace-intent binding: @ogs.play.games.…go
5

Resolution preview

When the current SIP resolves to a known destination — either because it is an owner-bound identity or matches a saved personal shortcut — the Owner-bound clickable SIP panel appears below the input.

  • The SIP string is rendered as a clickable link. Clicking it opens the destination URL in a new tab.
  • The resolved URL is shown in a read-only field. Click Copy URL to copy it to the clipboard.
  • A caption explains whether the resolution comes from a direct owner-bound path or from a saved personal shortcut.
Tip: Resolution is deterministic only for owner-bound SIPs. Discovery paths return ranked candidates because no single owner has been committed.
6

Favorites

Favorites (bookmarks) let you save any SIP string from the input for quick recall — useful when exploring a long path you want to return to later. Unlike personal shortcuts, a favorite simply stores the exact SIP string; it does not create an alias.

Saving a favorite

  1. Type or navigate to the SIP string you want to bookmark.
  2. Click the ☆ Favorite button in the actions bar.
  3. A Save to Favorites form slides into the bottom of the suggestion panel.
  4. Optionally type a name for the bookmark. Leave the field blank to use the SIP string itself as the name.
  5. Click ★ Save. The form closes and the bookmark appears in the ★ Favorites card in the right sidebar.

The button turns gold and reads ★ Favorited whenever the current input matches a saved bookmark. Navigating away (or typing) resets it to ☆ Favorite.

Loading a favorite

Click Load next to any entry in the Favorites card. The SIP input is immediately set to that string and the suggestion panel refreshes.

Removing a favorite

Click ✕ next to any entry in the Favorites card to delete it from this session.

Session scope: Favorites are stored in JavaScript memory and are cleared when the page is reloaded. In a real implementation they would persist in a user profile or browser storage.
7

Personal shortcuts

A personal shortcut is a compact alias — such as @games.lasca — that the resolver expands to a longer SIP in your trusted context. Shortcuts are more powerful than Favorites: they create a named alias that participates in IntelliSense and resolution.

Saving via shortcut binding (resolver-assisted)

  1. Type a shortcut path such as @games.lasca (or click Try @games.lasca).
  2. Owner-bound candidates appear in the suggestion panel under Shortcut discovery candidates.
  3. Click Save @games.lasca as my shortcut next to the candidate you prefer.
  4. The shortcut is saved. Entering @games.lasca now shows a saved shortcut row with options to expand or clear it.

Saving via freeform entry

  1. Navigate to any SIP with a registered semantic (two or more segments).
  2. In the Create freeform shortcut section at the bottom of the panel, type your desired alias (e.g. my.lasca).
  3. The hint line shows the normalised alias as it will be saved.
  4. Click Save shortcut.

Using saved shortcuts

Click My shortcuts in the top-right corner of the SIP input to open a dropdown listing all saved shortcuts for this session. Clicking an entry loads the full canonical SIP into the input.

Clearing shortcuts

Click Clear saved shortcut in the suggestion panel when a saved shortcut suggestion is visible, or click Clear saved shortcut in the actions bar to remove all personal shortcuts.

Session scope: Personal shortcuts live in JavaScript memory and reset on page reload. They do not create global ownership — the shortcut resolves only within this user context.

Sharing, import & manage

Personal shortcuts become more powerful when shared. The My shortcuts dropdown lets you export your collection as a sip-shortcuts/1.0 JSON file and import collections from others. Sharing works across three tiers — anonymous, identified, and globally published — each requiring progressively more identity verification.

Your SIP identity

The Your SIP identity field below the SIP input sets the email address that identifies you as an author. It is optional — you can share shortcuts without it. When set, it unlocks identified sharing and the global publishing options.

In a real implementation this field would be pre-populated from a verified browser profile or federated identity provider. The email address must be confirmed via ownership verification (e.g. a magic link or one-time passcode) before the system treats it as trustworthy. The mockup allows free entry so you can explore all sharing flows without authentication.

Opening the shortcuts panel

Click the My shortcuts ▾ button at the top-right of the SIP input card. The dropdown shows your saved shortcuts, any imported collections, and the sharing controls at the bottom.

Tier 1 — Share anonymously

Click ↑ Share anonymously to download your shortcuts as a JSON file with no author information. Anyone can import the file, but recipients cannot verify who created it and it cannot be published to the global SIP registry.

Tier 2 — Share as (identified)

Click ↑ Share as <your identity> to download an identified package. The file includes an author field containing your email and display name so recipients know who shared the collection. The button is disabled until you set a SIP identity in the field below the input.

  • When no global publishing SIP is set, the button label shows your raw email address. The author field is included in the export but no publishedAt registry address is attached.
  • When a global publishing SIP is set, the button label changes to that SIP address and the publishedAt field is embedded in every subsequent export.

Tier 3 — Global publishing SIP

The Global publishing SIP section at the bottom of the dropdown lets you register a stable, globally unique SIP address for your shortcut collection. This address is embedded in identified exports so recipients and resolvers know where to find the canonical, registry-verified version.

Two options are available:

Option 1 — Use derived

Click Use derived to set your publishing SIP automatically from your email address using the rule {local}@{domain} → @{domain}.{local}.shortcuts. Examples:

  • alice@example.com → @example.com.alice.shortcuts
  • edbecnel@gmail.com → @gmail.com.edbecnel.shortcuts

Global uniqueness is anchored to the email domain. For a custom domain this requires DNS or SIP manifest verification. For a managed provider (Gmail, Outlook, etc.) the provider vouches for the sub-identity on your behalf.

Option 2 — Provider-assigned

A federated SIP identity provider may issue a publishing SIP from within their own verified namespace. Enter the provider-assigned address in the text field and click Set. Example: @com.provider.alice.shortcuts. The address must be an owner-bound identity — discovery paths are not accepted.

Option 3 — Clear

Click Clear to remove the global publishing SIP. Subsequent identified exports will include the author field but no publishedAt address.

The Share button label updates immediately. Once you set or clear a global publishing SIP, the Share button label changes to reflect the new state — either the publishing SIP address or your raw email as a fallback.

Importing a shortcut collection

Click ↓ Import in the shortcuts dropdown and select a sip-shortcuts/1.0 JSON file. The client validates the schema and stores the collection.

  • Identified packages are listed under the author's name and email.
  • Anonymous packages are listed under a timestamped anonymous label.
  • A publishedAt address in the package is displayed as advisory — a real resolver would independently verify it before treating it as globally confirmed.
  • You cannot import your own exported package — your bindings are already in your personal shortcuts.

Precedence — your shortcuts win

If an imported collection defines the same shortcut alias as one of your personal bindings, your binding takes precedence. The imported binding is retained but marked as shadowed and will not be used for resolution. Imported shortcuts can never silently override your deliberate choices.

Managing your shortcuts

Click the ⚙ Manage button in the footer of the shortcuts dropdown to open the Shortcut Manager panel. The manager provides a dedicated interface for editing and deleting both your personal shortcuts and any imported collections.

My Shortcuts

The My Shortcuts table lists every personal shortcut you have saved. Each row shows the alias and the target SIP it expands to, with two action buttons:

  • Edit — replaces the row with two inline inputs. Adjust the alias, the target SIP, or both, then click Save to commit or Cancel to discard. If you change the alias key, the old key is removed and replaced with the new one.
  • Delete — permanently removes the binding from your personal shortcuts.

Imported Collections

Each imported collection is listed under a header showing the author name and email (or a timestamped anonymous label), the shortcut count, and the publishedAt SIP address if one is present. Within each collection you can:

  • Click Remove all in the collection header to delete the entire collection at once.
  • Click Delete on an individual binding row to remove just that one binding. If the last binding is removed the collection is also cleaned up.
  • Bindings whose alias matches one of your personal shortcuts are highlighted in amber with a (shadowed) label — they are retained for inspection but never used for resolution.
Close the manager by clicking ✕ Close in the panel header, pressing Esc, or clicking the dark backdrop behind the panel.
Session scope: Imported collections and the global publishing SIP setting live in JavaScript memory and reset on page reload. In a real implementation they would persist in a user profile.

Search

The Search SIPs bar at the top of the page lets you find any registered SIP path by keyword using a boolean query language. Clicking a result loads it into the SIP input.

Query syntax

chessMatch SIPs containing chess.
chess checkers or chess | checkers or chess, checkersOR — match SIPs containing either word.
chess & columns or chess + columnsAND — match SIPs containing both words.
!chessNOT — exclude SIPs containing chess.
(chess | checkers) + columnsGrouping with parentheses for complex queries.
chess | checkers
Finds all SIPs that mention chess or checkers.
lasca + stackworks
Finds SIPs that mention both Lasca and StackWorks.
columns !chess
Finds SIPs with "columns" but not "chess".

Synonym awareness

The search engine understands the semantic synonyms defined in the mockup. Searching for stacking will also surface SIPs that use the equivalent term columns (and vice versa), because the synonym map links them.

Bound only filter

Tick the Bound only checkbox to restrict results to SIPs that have a registered destination URL.

Keyboard navigation in results

Press ↓ from the search box to move focus into the results list. Use ↑ / ↓ to navigate between items, Enter to load a result, and Esc to clear the search.

Sidebar panels

★ Favorites

Lists all SIP strings you have bookmarked in this session. Each entry shows its name, the underlying SIP (if different from the name), a Load button, and a ✕ remove button. See § 6 Favorites for the full workflow.

Current interpretation

A live status panel that reflects the current SIP input:

  • Mode — Which of the five modes applies (discovery, owner-bound, shortcut, broad facet, personal shortcut binding).
  • Meaning — A plain-language description of what the current string represents.
  • Resolution behavior — Whether the resolver would return candidates, resolve deterministically, or request narrowing.
  • Destination preview — The URL the SIP resolves to, if one is registered.

Core UX rule

A fixed reference card explaining the fundamental distinction between semantic exploration (typing categories) and identity commitment (choosing an owner-bound result). The explanatory text also covers shortcuts, synonyms, and broad facets.

Selection history

A running log of every action taken in the mockup — segment selections, shortcut expansions, owner identity commits, shortcut saves, favorites saves, and more. The most recent action appears at the top. The log is capped at twelve entries.

Glossary

SIP — Semantic Identity Path
A dot-separated, human-readable string prefixed with @ that encodes the identity of a concept through a chain of semantic categories. Example: @games.strategy.abstract.capture.leaping.columns.lasca.
Discovery path
A SIP that begins with a semantic category rather than an owner namespace (e.g. @games.…). It explores meaning but does not commit to a single owner or destination.
Owner-bound identity
A SIP whose first segment is an owner namespace (e.g. @stackworks.…). The resolver can deterministically route this to the owner's registered destination.
Shortcut SIP
A compact alias SIP such as @games.lasca that expands to a longer path. A discovery shortcut expands to a longer semantic path; an owner-bound shortcut such as @stackworks.games.lasca expands to the canonical owner-qualified identity.
Personal shortcut binding
A user-saved mapping from a compact alias to a specific owner-bound SIP, stored in the user's trusted context. It does not create global ownership — the binding applies only to the current user.
Semantic synonym
Two path segments that carry identical meaning within a given context. For example, columns and stacking are synonyms in the leaping-capture branch of the games taxonomy. Either segment produces the same set of results.
Broad semantic facet
A high-level cross-cutting concept (e.g. stacking under abstract strategy) that matches multiple narrower branches rather than collapsing to a single canonical path. The resolver presents narrower-path suggestions instead of resolving directly.
Resolver
The system that interprets a SIP string, consults registered owners, and either returns ranked candidates (discovery) or redirects deterministically (owner-bound).
Favorite / Bookmark
A saved copy of any SIP string, stored with a user-defined name, for quick recall. Unlike a shortcut, a favorite does not create an alias — it preserves the exact SIP string as-is.
Trust level
An indication of how confidently an owner candidate has been verified. The mockup uses two levels: Domain Verified (owner is confirmed) and Candidate (plausible but unverified).
Resource-type qualifier
A path segment or structural convention that communicates the kind of resource a binding offers — for example, whether a destination is a place to play a game, read about it, or purchase it. SIP supports three coexisting approaches: terminal qualifiers (Option A), owner-implicit binding (Option B), and namespace intent (Option C).
Terminal qualifier binding (Option A)
A binding where the resource type is expressed as a final child segment of the concept path. Example: @ogs.games.strategy.abstract.territory.enclosure.go.online. The online segment is the terminal qualifier. These segments are navigable via IntelliSense as ordinary discovery continuations.
Owner-implicit binding (Option B)
A binding where the resource type is implied by the owner's well-known profile, without any additional path segment. Example: @ogs.games.strategy.abstract.territory.enclosure.go — OGS implies a playable destination. This is the default form used throughout the mockup.
Namespace intent (Option C)
A binding where an intent segment is inserted between the owner namespace and the discovery path. Example: @ogs.play.games.strategy.abstract.territory.enclosure.go. The play segment is the intent qualifier. This form is fully self-describing and does not require out-of-band knowledge of the owner's profile.
sip-shortcuts/1.0
The JSON schema used for exporting and importing shortcut collections. Every package includes a schema field set to "sip-shortcuts/1.0", a bindings array, and optional author, publishedAt, label, and created fields.
Anonymous shortcut package
A sip-shortcuts/1.0 export with no author field. Can be freely distributed and imported, but cannot be published to the global SIP registry and carries no author attribution.
Identified shortcut package
A sip-shortcuts/1.0 export that includes an author field with the exporter's verified email address and display name. Identified packages are a prerequisite for global publishing. The email must be ownership-verified before the author field is considered trustworthy by a recipient or resolver.
publishedAt
An optional field in an identified shortcut package that records the globally unique, owner-bound SIP address where the collection is registered in the SIP registry. Recipients should treat this value as advisory until a resolver independently verifies the package at that address.
Domain-derived publishing SIP
A globally unique publishing address derived automatically from the user's email: {local}@{domain} → @{domain}.{local}.shortcuts. Uniqueness is anchored to the email domain, which must be verified by DNS ownership proof or vouched for by a managed email provider.
Provider-assigned publishing SIP
A publishing address issued by a federated SIP identity provider from within their own verified owner namespace. Does not require the user to own a domain. Trustworthy only if the provider's root namespace is itself registered and verified in the SIP registry.
Shadowed binding
An imported shortcut binding that shares the same alias key as one of the user's personal shortcuts. The personal binding always wins; the imported one is retained but marked shadowed and excluded from resolution. Shadowing ensures imported collections cannot silently override deliberate personal choices.
Shortcut manager
A full-screen panel opened via the ⚙ Manage button in the shortcuts dropdown footer. Provides full CRUD for personal shortcut bindings — inline edit of alias and target SIP, delete individual bindings — and collection-level controls for imported packages — remove a single binding or the entire collection. Shadowed bindings are highlighted amber in the manager.
Help file for the SIP IntelliSense standalone mockup. No external libraries or network requests.
